Section 1Charter and rationale

Purpose. The Knowledge Web is a prototype interface that renders a body of work as a navigable orb web, backed by an ontology, a taxonomy, a thesaurus and a reasoner. It exists to reduce the cost of re-finding, connecting, explaining and handing over accumulated knowledge — and to make absence visible, not only presence.

Why this record is decoupled

Separation of concerns

Governance is not a feature

The operational prototype should carry no obligation to render its own backlog. Embedding governance couples release cadence to documentation cadence.

Independent lifecycle

Different clocks

The prototype changes per build session. This authority changes per decision. Neither should force a version bump in the other.

Artefact custody

Survives environment reset

The operational code line has, to date, existed only as build-session output with no durable version control. This record is self-contained and portable — it survives exactly the conditions that threaten the code line. See R-02.

Doctrinal consistency

Applied to itself

The programme holds that AI must be augmentation, never load-bearing infrastructure. The same structural-resilience principle is applied to documentation.

The alignment contract

This authority and the operational prototype are siblings, not parent and child. Reference, not derivation: this record references the prototype's capabilities and gaps; it does not generate them, and the prototype does not read from it. Where they disagree, the prototype is the statement of what exists and this record is the statement of what was decided.

Section 2Foundational doctrine

Adopted from the Whitehall Connect GOV-2.8 Programme & Architecture Authority, because the same constraints apply and doctrine that differs between sibling artefacts is not doctrine.

The four tenets

TenetStatementHow this prototype holds it
T-01Augmentation, not dependency. AI accelerates human work; it never becomes the only path to an outcome.Held. Every reading the interface offers — class, purpose, ladder band, route — is also reachable through the text version and the reference tables.
T-02Registered fallback. No AI capability ships without its manual counterpart logged in the Augmentation Register.Partially held. Register created at Section 6; three entries still lack a documented manual counterpart.
T-03Degraded-mode completeness. With every service unavailable, the artefact still performs its core function end to end.Not held. The prototype is entirely JavaScript-rendered and fetches web fonts from a CDN. See BL-WEB-01 and BL-WEB-02.
T-04Human-in-the-loop on consequence. Anything that drafts, decides or acts on the user's behalf surfaces for explicit human review.Held. The prototype asserts nothing on the user's behalf. Inferred axioms are visually separated from asserted ones and can be switched off; induced patterns are separated again from both.

Honesty and data posture

  • All content is either the user's own conversation history or workbooks the user supplied. No live government system is contacted. No external data is fetched at runtime other than typography.
  • Nothing is stored, transmitted or persisted. Preferences and navigation history exist in memory for the session only.
  • Honest prototype labelling is maintained throughout and never obscured. The home page carries it above the fold.
  • UK English exclusively — artefact, behaviour, centre, organised, prioritise.
  • Where a reading is inferred it says so. Where a scheme is unconfirmed it stays unconfirmed until confirmed by its owner.

Doctrine self-test, applied to this prototype

Three honest failures. One: the operational prototype renders nothing with JavaScript disabled, so it fails degraded-mode completeness outright. Two: it loads Google Fonts from a CDN, so it is not self-contained on first paint and will not render as designed on an air-gapped or egress-restricted desktop. Three: it has been tested by automation only — never with a user, and never with a screen-reader user. Accessibility here is built to WCAG 2.1 AA intent and verified against contrast and keyboard criteria; it is not assured. All three are carried as P1 backlog items rather than caveated away.

IA-01No entry point. The user landed in the middle of a tool with no orientation layer.The single most damaging finding. There was nothing that answered "what is this, what can I do, where do I start" before the interface demanded a decision. Portals need a threshold.Fixed

The organising principle

Destinations become pages. Modes stay with the thing they modify. Preferences collapse into one place. The previous build mixed all three in one row, which is why it read as complicated rather than capable. Owl view, strata and the lens correctly remain on the stage, because they change what the stage shows and nothing else. Theme and text scale correctly leave the stage, because they change everything.

On the compendium ambition

The multipage shell makes the playbook-compendium use case tractable, and it is the strongest of the candidate directions. The Data Governance Playbook becomes one collection among many across the end-to-end data and lifecycle management discipline — cataloguing, governance, quality, architecture, ethics, sharing, retention, records, mastering, valuation. Each playbook is a web; the compendium is the collection registry; the shared ontology, taxonomy and thesaurus are what make cross-playbook navigation possible rather than merely adjacent.

The condition is BL-WEB-03: until collections can be authored from a source file rather than hand-written, the compendium cannot grow past the pace of hand-authoring. That single item is the difference between a demonstrator and a platform.

Level 3 — the collection contract

Any collection must supply: strands[] each with nodes[]; themes[] for cross-thread crossings; enrich{} giving each node a class, taxonomy path, ladder band and typed relations; and repairs[] — the torn strands. The last of these is not optional. A collection that declares no gaps is not trusted by this system, because every real body of work has them and a claim of completeness is itself a finding.

Section 12Alignment register

Terminology finding: three meanings for KIL

KIL currently denotes at least three different things across DSIT/GDS artefacts: the Knowledge Integration Layer (KISIL specification, section 1); Keystone Up the Chain (Whitehall Connect relocated working views); and a named view in the Data Sharing Observatory. This prototype adopts the KISIL definition as canonical and renames its own inferred ladder to KSL. The wider collision is carried as BL-WEB-37 and is a governance matter, not a UI one — an acronym with three referents inside one directorate will eventually cause a real misunderstanding in a real decision.

Section 14Build and validation conventions

  • Assembly. Authored as ordered chunks, concatenated to a single file. Every inline script extracted and passed through node --check before the build is considered valid.
  • Validation. Headless browser render with console and page-error capture; interaction sweep across every control; contrast measured programmatically against the painted background, not the declared one.
  • Defect handling. Defects found during validation are named in the release history rather than quietly fixed. Four have been recorded so far.
  • Typography. UK English exclusively. Literal · (U+00B7) and — (U+2014) in prose; JS escapes inside template strings, to avoid anchor mismatch during patch runs.
  • Paths. Outputs to /mnt/user-data/outputs/. Uploads are read-only.
  • No storage APIs. localStorage and sessionStorage are not used anywhere, by decision ADR-W08.
